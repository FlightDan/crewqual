# 资质数据核查与兼容退出门禁

## 只读核查

在已完成增量迁移的目标环境中显式注入 `DATABASE_URL`（或优先的 `DIRECT_URL`），运行：

```sh
pnpm exec tsx scripts/audit-qualification-state.ts --dry-run
pnpm exec tsx scripts/reconcile-member-architecture.ts
```

脚本不加载仓库 `.env`，不修复、补齐或删除数据；所有读取使用一个 `REPEATABLE READ / READ ONLY` 事务和一次捕获的当前时间。输出按组织分组，并按成员、定义、记录、分类及原因排序，实体 ID 区分申请、计划和材料关联。只输出 ID、固定原因和计数，不输出证照字段、材料位置、URL、凭据或完整规则快照。失败仅输出固定错误，详细连接异常不进入发布日志。大型库需在受控环境评估运行时间与内存；当前实现完整读取成员关系和记录，并有 120 秒事务超时，超时属于失败而非零问题。

分类：

| 分类                    | 依据                                                                                                |
| ----------------------- | --------------------------------------------------------------------------------------------------- |
| required_missing        | 共享成员投影的有效分配合并后必需，且无记录；包含无任何记录的成员                                    |
| incomplete              | 共享保存快照状态判定返回不完整；覆盖历史及有效记录                                                  |
| timezone_conflict       | 单位时区缺失、非法、Person/Pilot 单位冲突或组织关系异常                                             |
| unverified_snapshot     | 无效/缺失快照或 inferred_backfill；不将推断长期有效视为证明                                         |
| legacy_pending_baseline | PENDING 且 baselineCapturedAt 为空，禁止补猜历史提交基准                                            |
| duplicate_active        | 新 person/definition 或旧 pilot/type 组合多个 ACTIVE，按涉及记录输出                                |
| canonical_link          | 记录/申请缺新关联、Person/Pilot 或定义类型/组织不一致、旧 Pilot 缺 Person、计划缺关联或职位归属错误 |
| duplicate_evidence_pair | 相同 image 与 record 或 request 重复；材料跨不同历史修订复用合法                                    |

计数是问题条目数，不是受影响人员数；同一记录可以同时属于多个分类。未执行生产存量扫描时，实际影响数量为**未知**。受控 fixture 或空库结果不能作为生产影响数量。

## 两种门禁

业务修复发布：audit 默认报告模式，执行完整返回 0，即使发现待人工处理的问题；执行失败返回 1。发布必须保存报告并明确遗留数据处置人和计划，验证程序确实展示缺失/不完整并阻止无基准审批。不能为了“归零”制造记录或日期。修复发布不要求所有旧历史数据预先修完。

兼容删除发布：reconcile 与 audit 的 `--gate=compatibility` 使用同一报告；任何问题返回 2，执行失败返回 1，只有零问题返回 0。这是删除兼容的必要条件，不是充分条件。严格门禁不能代替行为对账、写入来源检查、观察期或回退验证，也不能仅凭核查脚本存在就声称迁移完成。

发布 full 验收应分别记录：候选 commit/镜像摘要、迁移版本、核查命令及退出码、脱敏报告位置、观测区间、覆盖实例和缺口。修复版本保存 report 结果；未来删除兼容候选还必须运行 strict reconcile。不要用 strict 数据归零要求阻止修复代码上线。

## 观察与退出条件

`observeCompatibilityPath` 仅接受固定标签 `legacy_cookie`、`legacy_api`、`legacy_record_fallback`，每次调用产生 count=1 的结构化日志。集成点应是成功使用旧 cookie 的认证分支、实际旧 `/api/pilot` 请求入口（避免 `/api/member` re-export 被误算）、实际采用 legacy record 的读取分支。每个行为在统一边界计数一次。日志采集器按版本、实例及标签聚合，不记录 cookie、token、原始 URL 或材料内容；采集器负责部署元数据。函数存在本身不表示所有入口已接入。

建议版本安排：当前业务修复版本保留兼容；随后一个独立版本完成所有写入口切换和观测接入；最早再后一个独立版本才考虑删除。最终版本号由发布负责人指定，不能将日期或建议当作已经批准的退出版本。

开始观察前：生产及灾备迁移对账为零、全量新字段完整、跨组织与历史链核查通过、所有 web/worker/导入/脚本写入均切换，旧实例已退出，双路径在受控相同快照下逐项一致，并有可复现证据。

建议连续至少 30 天且不少于最长有效会话/访问链接寿命，并覆盖一次完整日常提醒、备份恢复及部署回退演练。所有实例与 worker 观测完整；必要旧路径使用必须为零。任何必要旧使用、采集缺口或新对账差异均修复后重新开始计时，不能把进程重启后的空计数当作完整观察期。外部旧 API 消费者需确认完成切换；旧路由探测与真实业务使用在复核记录中区别说明，不记录敏感请求。

删除前使用仍保留审批 ID+版本保护的兼容回退版本演练；不得回退到绕过新审批保护的旧应用。只有严格核查为零、上述观察期与行为证据完整、退出版本确定后才单独删除旧 Cookie/API/字段。Person/Pilot 兼容模型不在本次业务修复中删除。
