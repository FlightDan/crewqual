# 主体、客体及访问边界

本文定义 CrewQual 实际使用的身份与资源归属规则，供实现、测试和安全审计共同使用。它不把字段名称或页面入口本身当作访问控制已经成立的证据。GB/T 22239-2019 8.1.4.2 g) 的差距结论还应结合入口覆盖、负向验证及部署证据判定。

## 标记来源与判定

| 主体/客体                    | 可信标记来源                                                             | 访问规则                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 管理员主体                   | 有效会话关联的 AdminUser、当前角色权限、unitId、organizationId           | 每次请求重新读取身份；功能权限与数据范围分别检查，两者同时成立才允许操作                    |
| 成员主体                     | 有效 PilotSession 关联的 Pilot、Person、PilotProfile 和 OrganizationUnit | 输出 pilotId（兼容字段 id）、personId、organizationId、unitId；缺失、禁用或关系冲突拒绝访问 |
| 人员、资质、申请、岗位分配   | 数据库中的 Person/Pilot 及父子资源关系                                   | 成员只能访问本人；普通管理员限制在分配单位，并满足相应操作权限                              |
| 证照及识别结果               | EvidenceImage 的人员归属与关联记录                                       | 校验当前主体、图片所属人员及父资源一致后，才允许签发 URL、识别或关联                        |
| 系统设置、备份、安全配置     | 资源类型及专门权限                                                       | 使用系统级权限，不能因为管理员可进入后台就授予访问                                          |
| 管理员收件箱、会话、认证因素 | 数据库记录的管理员 ID 或成员 ID                                          | 按本人和各接口的附加验证规则处理，不继承全局超管数据范围来修改他人因素                      |

SUPER_ADMIN 在人员及其业务资源的新旧范围 helper 中均为全局范围，即使账号保存了单位或组织也不缩小该范围。普通管理员没有单位时默认拒绝；成员目录同时使用组织条件（存在时）和单位条件。单位 ID 在数据库中全局唯一，旧 Pilot 查询以单位 ID 限定范围。范围 helper 仅构造数据查询条件，不能替代 `getAdmin` 的权限、会话和写操作验证。

## 成员身份一致性

`authenticatePilot` 同时加载会话关联的 Pilot、Pilot.person、Person.pilotProfile、Pilot.profile、Pilot.unit，检查：

1. Pilot 和 Person 均启用，Pilot.personId 等于 Person.id。
2. Person 有单位和组织，Person.unitId 等于 Pilot.unitId，单位的组织等于 Person.organizationId。
3. 正反两侧 Profile 是同一条记录，Profile.personId 和 legacyPilotId 分别等于当前 Person 和 Pilot。

成员 cookie 和旧 pilot cookie 使用同一认证函数；成员 API 直接导出对应 pilot handler。查询、body、URL、cookie 自述字段均不能成为归属依据。处于额外认证绑定阶段的会话即使允许访问绑定接口，也必须先满足上述身份一致性。

迁移后的规范身份关系是认证前提。未完成成员迁移、关系缺失或相互冲突的历史数据不得回退到仅凭 Pilot.id 授权；应先通过既有成员迁移/核对流程修复。成员调动后，下一次认证重新读取当前单位，不沿用会话创建时的单位副本。

## 写入及后台任务边界

归属字段只能由服务端根据认证身份或已授权父资源生成。人员调动、岗位分配、导入、资质修订等管理操作要检查权限并记录变更。修改关联前检查父子资源一致性，不能让客户端通过改变 personId、pilotId、unitId、recordId 或 objectKey 扩大范围。

识别、图片优化、通知和备份任务是系统主体，不是匿名用户。任务载荷中的资源 ID 只作为定位信息；执行时需要重新读取可信资源关系和状态。任务不能把任意外部 objectKey 当作已授权资源。具体 worker 边界应由相应任务的测试覆盖，路由登记测试不能证明后台任务安全。

签名 URL 在签发前检查权限；现有存储下载凭据最长有效 300 秒。在凭据过期之前，注销会话或修改归属不保证已经签发的链接立即失效。不得把这个机制描述为每次对象存储下载都重新验证应用会话。

## 机器清单与验证

`src/server/access-control-inventory.ts` 显式登记每个 API 路由模板、导出 HTTP 方法、主体、客体、动作和范围类别，供入口分类和审计使用。它不授予权限，不替代路由中的鉴权。

`access-control-inventory.test.ts` 使用 TypeScript AST 对比实际路由及导出方法，新增路由、遗漏方法、过期登记、通配导出都会使测试失败；成员别名必须保持直接导出对应 pilot handler。分类 helper 按静态片段优先匹配，并考虑框架提供的 HEAD/OPTIONS。

以下针对性测试构成身份与范围证据：

- `auth-member-identity.test.ts`：规范身份、缺失或冲突关系、禁用身份、新旧 cookie、一致性失败不刷新会话、调动后重新读取范围。
- `admin-permissions.test.ts`：四种管理员角色权限、新旧全局超管范围、普通管理员无单位拒绝。
- `member-repository.test.ts`：列表、计数和详情范围，超管携带组织时仍全局。
- `access-control-inventory.test.ts`：路由/方法登记、别名同源及入口匹配。

完整资源验收还须扩展 `e2e/remote/qualification-scope.spec.ts`：两个组织及单位、同单位两名成员、四种管理员角色；测试本人/他人/跨单位/跨组织、列表/计数/导出、嵌套 ID 错配、伪造归属、新旧 API、证照与识别、归属变更。拒绝断言应同时证明无数据、无签名 URL、无写入和无新任务，不能仅断言状态码。

有通过的入口证据后才关闭相应差距；未验证的接口、任务、数据迁移和部署行为继续保留为待验证。
